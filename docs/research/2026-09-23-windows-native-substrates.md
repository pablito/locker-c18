# Windows-native environment substrates for Locker

## Question

Which environment substrates can support Locker-generated repositories on Linux, WSL2, and native Windows from one repo-level definition, without requiring `curl | bash`, while still allowing AI agent CLIs to run on native Windows?

## Summary

- Devbox remains viable on Linux and WSL2, but Jetify documents Windows only through WSL2 and the Nix manual lists supported platforms as Linux/macOS, so it is not a native-Windows substrate today ([Jetify](https://www.jetify.com/docs/devbox/installing-devbox/), [Nix manual](https://nix.dev/manual/nix/latest/installation/supported-platforms)).
- Native Windows support is strongest for mise, pixi, proto, and Volta; asdf is WSL2-only/Unix-oriented in official docs and releases ([mise](https://mise.jdx.dev/installing-mise.html#windows-scoop), [pixi](https://pixi.prefix.dev/latest/installation/), [proto](https://moonrepo.dev/docs/proto/install), [Volta](https://docs.volta.sh/guide/getting-started), [asdf FAQ](https://github.com/asdf-vm/asdf/blob/master/docs/more/faq.md)).
- mise and proto provide the closest direnv-like native Windows story through shell activation/shims that react to directory context ([mise activate](https://mise.jdx.dev/cli/activate.html), [proto detection](https://moonrepo.dev/docs/proto/detection)).
- pixi supports native Windows and `pixi shell-hook`, but automatic enter-directory activation is officially shown through direnv, whose own prerequisite is a Unix-like OS ([pixi shell-hook](https://pixi.prefix.dev/latest/reference/cli/pixi/shell-hook/), [pixi direnv](https://pixi.prefix.dev/latest/integration/third_party/direnv/), [direnv](https://direnv.net/)).
- Volta is native Windows-friendly but only manages JavaScript command-line tools via `package.json`, so it is not a general multi-runtime substrate ([Volta understanding](https://docs.volta.sh/guide/understanding)).
- Plain PowerShell+Bash scripts and “no substrate” are viable as Locker-owned designs, but their behavior is implementation-defined and cannot be verified from external primary docs.
- Copilot CLI, Claude Code, OpenCode, and Codex CLI all document native Windows install paths that do not require `curl | bash` ([Copilot](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/install-copilot-cli), [Claude Code](https://docs.claude.com/en/docs/claude-code/setup), [OpenCode](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/index.mdx), [Codex](https://github.com/openai/codex)).
- Docker Desktop is free only for small businesses under both 250 employees and $10M revenue; for a ~50-dev org this depends on the legal entity revenue/headcount, not just dev-team size ([Docker](https://docs.docker.com/subscription-billing/desktop-license/)).

## Findings per substrate

### Devbox / Nix

Jetify documents Devbox prerequisites as the Nix Package Manager and says Devbox can automatically install Nix if it is missing ([Jetify install](https://www.jetify.com/docs/devbox/installing-devbox/)). Jetify’s Windows path is explicitly “Windows/WSL2”: “You can use Devbox on Windows using Windows Subsystem for Linux 2,” then run the install script in the WSL2 terminal, and Devbox installs Nix in single-user mode for WSL2 if needed ([Jetify install](https://www.jetify.com/docs/devbox/installing-devbox/)). Jetify documents `devbox generate direnv` as the generated `.envrc` path for automatic shell setup, which requires installed direnv and Devbox ([Jetify direnv](https://www.jetify.com/docs/devbox/ide-configuration/direnv/)). Nix’s own “Supported Platforms” page lists Linux and macOS, not Windows, as currently supported platforms ([Nix supported platforms](https://nix.dev/manual/nix/latest/installation/supported-platforms)). Nix has current native-Windows issue traffic—e.g., an open issue about `nix.exe` cross-compiled for `x86_64-w64-mingw32` having unresolved absolute-path semantics—so native Windows appears experimental/unfinished rather than a supported substrate ([Nix #16412](https://github.com/NixOS/nix/issues/16412)). The older Nix issue “Port Nix to Windows, Natively or MinGW+MSYS2” confirms the project has tracked native Windows as a porting target, but that issue is not proof of production support ([Nix #1365](https://github.com/NixOS/nix/issues/1365)).

### mise

mise documents Windows installation through Scoop, winget, Chocolatey, and manual GitHub release download ([mise install](https://mise.jdx.dev/installing-mise.html#windows-scoop)). mise also documents Linux/macOS installation via `mise.run`, package managers, cargo, npm, GitHub Releases, Nix, and other distribution package managers ([mise install](https://mise.jdx.dev/installing-mise.html)). `mise activate` supports `bash`, `zsh`, `fish`, `nu`, `xonsh`, `elvish`, `pwsh`, and `powershell`, and its docs state activation updates tools and environment variables as the shell changes directories ([mise activate](https://mise.jdx.dev/cli/activate.html)). mise shims default to `~/.local/share/mise/shims` on Unix and `%LOCALAPPDATA%\mise\shims` on Windows ([mise shims](https://mise.jdx.dev/dev-tools/shims.html)). The Linux GNU binaries require glibc 2.18+ unless a musl build is selected ([mise install](https://mise.jdx.dev/installing-mise.html)).

### pixi

Pixi’s documentation describes it as a cross-platform package manager and project management tool using `pixi.toml` and `pixi.lock` ([pixi llms](https://pixi.prefix.dev/latest/llms.txt)). Pixi documents Windows installation through an `.msi` installer, winget, Scoop, a PowerShell installer, and GitHub releases, and says Pixi is a single executable without external dependencies ([pixi install](https://pixi.prefix.dev/latest/installation/)). `pixi shell-hook` prints activation scripts and includes a PowerShell example, `(pixi shell-hook) | Out-String | Invoke-Expression` ([pixi shell-hook](https://pixi.prefix.dev/latest/reference/cli/pixi/shell-hook/)). Pixi’s official automatic directory-entry tutorial uses direnv and an `.envrc` that evaluates `pixi shell-hook`; that gives enter/leave behavior only where direnv itself is available ([pixi direnv](https://pixi.prefix.dev/latest/integration/third_party/direnv/), [direnv](https://direnv.net/)). Pixi has WSL caveats around `pixi shell` and `wsl.exe` taking over stdin, but this is a shell caveat rather than an install-platform statement ([pixi advanced shell](https://pixi.prefix.dev/latest/advanced/pixi_shell/)).

### asdf

asdf’s README says it automatically switches runtime versions as directories change and uses a single `.tool-versions` file per project ([asdf README](https://github.com/asdf-vm/asdf)). The official FAQ says WSL1 is not officially supported and WSL2 should work only when the current directory is on a Unix drive rather than a bound Windows drive ([asdf FAQ](https://github.com/asdf-vm/asdf/blob/master/docs/more/faq.md)). The current getting-started source lists Homebrew, Zypper, Pacman/AUR, precompiled binaries, Go install, and source builds; it configures shims for Bash, Fish, Elvish, Zsh, PowerShell Core, Nushell, and POSIX shells ([asdf getting started](https://github.com/asdf-vm/asdf/blob/master/docs/guide/getting-started.md)). The v0.20.2 release assets list Darwin and Linux archives and no Windows archive, so native Windows support could not be verified from official release artifacts ([asdf v0.20.2 release](https://github.com/asdf-vm/asdf/releases/tag/v0.20.2)).

### Volta

Volta documents Unix installation through `curl https://get.volta.sh | bash`, Windows installation through winget, and an optional direct installer download ([Volta install](https://docs.volta.sh/guide/getting-started)). Volta says WSL users should follow the Unix installation guide ([Volta install](https://docs.volta.sh/guide/getting-started)). Volta’s scope is JavaScript command-line tools such as Node, npm, yarn, and executables shipped by JavaScript packages ([Volta understanding](https://docs.volta.sh/guide/understanding)). Volta detects which project is active based on the current directory and routes tool execution to versions pinned in `package.json` using `volta pin` ([Volta understanding](https://docs.volta.sh/guide/understanding)).

### proto (moonrepo)

proto documents Linux, macOS, WSL, and Windows install paths; Windows uses `irm https://moonrepo.dev/install/proto.ps1 | iex` in administrator PowerShell, while Unix/WSL uses a Bash installer around curl ([proto install](https://moonrepo.dev/docs/proto/install)). proto also documents manual installation from GitHub release assets ([proto install](https://moonrepo.dev/docs/proto/install)). proto’s configuration is the TOML `.prototools` file, with local Windows paths such as `.\.prototools` and global Windows paths such as `%USERPROFILE%\.proto\.prototools` ([proto config](https://moonrepo.dev/docs/proto/config)). proto’s default resolution traverses upward from the current directory for `.prototools`, and its detection page says shims trigger contextual version detection based on the current working directory ([proto config](https://moonrepo.dev/docs/proto/config), [proto detection](https://moonrepo.dev/docs/proto/detection)). proto’s install docs list Git plus tar/unzip/gzip/xz for fetching and unpacking archives, while also saying proto itself is shipped as two binaries and does not require external dependencies ([proto install](https://moonrepo.dev/docs/proto/install)).

### Plain scripts

A PowerShell+Bash substrate can be defined by Locker itself, so its Linux, WSL2, native Windows, install, activation, and dependency behavior is not externally verifiable from primary third-party docs. This option can avoid `curl | bash` if Locker ships scripts in the repo, but that is a design decision to be specified and tested by Locker rather than a claim available in primary sources.

### No substrate

A “no substrate” mode can be defined by Locker itself, where Locker only emits agent configuration files and assumes host runtimes are already installed. Its behavior is not externally verifiable from primary third-party docs because there is no third-party substrate. This option avoids substrate installation entirely, but shifts runtime/version responsibility to host provisioning.

## Agent CLIs on Windows

- GitHub Copilot CLI: official docs require PowerShell v6+ on Windows and offer WinGet (`winget install GitHub.Copilot`) and npm (`npm install -g @github/copilot`, all platforms, Node.js 22+) without requiring `curl | bash` on Windows ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/install-copilot-cli)).
- Claude Code: official docs list native Windows 10 1809+/Windows Server 2019+, PowerShell/CMD shells, Windows PowerShell installer (`irm ... | iex`), Windows CMD installer, WinGet (`winget install Anthropic.ClaudeCode`), and optional Git for Windows for Bash-tool support ([Claude Code setup](https://docs.claude.com/en/docs/claude-code/setup)).
- OpenCode: official docs recommend WSL for best Windows experience, but also list native Windows installation through Chocolatey, Scoop, npm, mise, Docker, and release binaries; Windows Bun install is “currently in progress” ([OpenCode docs source](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/index.mdx)).
- OpenAI Codex CLI: the official README documents native Windows installation through PowerShell (`irm ... install.ps1 | iex`) and npm (`npm install -g @openai/codex`), plus GitHub Releases for platform binaries; no official winget/scoop/MSI path was verified in that README ([OpenAI Codex README](https://github.com/openai/codex)).

## Docker note

Docker Desktop is governed by the Docker Subscription Service Agreement, and Docker’s license page says Docker Desktop is free for small businesses with fewer than 250 employees and less than $10 million in annual revenue, while paid subscriptions are required for larger organizations, government entities, and commercial use beyond free-tier limits ([Docker Desktop license](https://docs.docker.com/subscription-billing/desktop-license/)). For an organization with roughly 50 developers, the dev-team size alone does not answer the license question because Docker’s page frames the free tier as a business/organization threshold, so the actual legal entity’s employee count and annual revenue must be checked internally ([Docker Desktop license](https://docs.docker.com/subscription-billing/desktop-license/)). Docker’s page separately says licensing for Docker and Moby open-source projects such as Docker Engine is not changing, so this note is specifically about Docker Desktop ([Docker Desktop license](https://docs.docker.com/subscription-billing/desktop-license/)).

## Gaps / unverified

- I could verify that Nix’s manual lists only Linux/macOS as supported and that native Windows issues remain active, but I could not verify an official stable native Windows Nix installer or support statement; therefore native Nix is recorded as experimental/unfinished rather than supported ([Nix supported platforms](https://nix.dev/manual/nix/latest/installation/supported-platforms), [Nix #16412](https://github.com/NixOS/nix/issues/16412)).
- I could not verify native Windows asdf support from official release assets; official FAQ only verifies WSL2 expectations and v0.20.2 assets omit Windows archives ([asdf FAQ](https://github.com/asdf-vm/asdf/blob/master/docs/more/faq.md), [asdf v0.20.2 release](https://github.com/asdf-vm/asdf/releases/tag/v0.20.2)).
- Plain scripts and “no substrate” are Locker-owned approaches, so external primary-source verification is not possible until Locker specifies those contracts.
- Docker Desktop license applicability for Locker’s organization requires internal headcount/revenue/legal-entity confirmation; public Docker docs cannot verify pablito’s organizational facts ([Docker Desktop license](https://docs.docker.com/subscription-billing/desktop-license/)).
